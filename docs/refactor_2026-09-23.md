# Refactor de API y concurrencia · 23 de septiembre de 2026

## Diagnóstico comprobado

El cambio de perfil entraba en `with LOCK` y llamaba a `_get_active_profile`, que adquiría el mismo candado no reentrante. Con una cookie activa, la operación quedaba esperando su propio candado. La limpieza periódica también requería ese candado y podía bloquear la atención de nuevas solicitudes. La prueba aislada en `tests/benchmark_api.py` reprodujo el patrón del código anterior de Git.

Otros problemas encontrados:

- Conexión SQLite global compartida entre hilos.
- Tres implementaciones duplicadas de llamadas HTTP a Gemini, sin reutilización de cliente.
- Timeout uniforme de 50 segundos y bloqueo global de botones para cualquier acción.
- Cambio de perfil conservaba datos de revisión anteriores en la interfaz.
- La comparación podía acceder a `.description` de un lado inexistente de una coincidencia ambigua.
- La planificación de metas enviaba siempre `reductions: []`.
- La planificación de eventos transformaba importes vacíos en cero.
- Reemplazar un mes borraba el presupuesto anterior antes de intentar crear el nuevo.

## Implementación

- API FastAPI/Uvicorn en `spendwise_api.py`; `app.py` queda como arranque.
- Cliente HTTPX compartido en `spendwise_provider.py`, con conexiones persistentes y errores diferenciados.
- Cola asíncrona en `spendwise_jobs.py`: límite de concurrencia, plazo total, deduplicación, propiedad de resultados y cancelación.
- POST de IA devuelve 202; GET consulta el estado y DELETE cancela. No se mantiene una petición del navegador abierta durante toda la generación.
- Operaciones SQLite breves en el threadpool, conexión por operación y WAL. Los archivos y presupuestos existentes se conservan.
- Sustitución de presupuesto dentro de una transacción, manteniendo ID y rollback ante fallo.
- Cliente de navegador único en `web/api.js`, con cancelación, timeout local corto y descarte de respuestas obsoletas.
- Eliminación de ejemplos y modo ensayo de la aplicación. Se conservan fixtures únicamente como evidencia y herramientas de prueba.
- Creación/cambio de perfiles, edición de meses guardados, comparación y planificación conectados a la nueva API.
- Metas con reducciones editables por movimiento; eventos con montos explícitos y confirmación de supuestos.

## Evidencia

`python verify.py`: **50 pruebas aprobadas**, **11/11 evals offline**. El informe está en `evals/gates_report.json`.

`python tests/browser_smoke.py`: **9 comprobaciones de flujo aprobadas en Edge**, incluyendo perfil, análisis, guardado, edición, comparación/explicación, metas, eventos, cancelación y cambio de perfil con IA pendiente. Se emplea un proveedor inyectado de prueba; no hay fixtures disponibles en la aplicación productiva. Reporte: `evals/browser_report.json`.

Medición local con cliente HTTP en proceso, SQLite temporal y proveedor artificialmente demorado dos segundos (`evals/performance_report.json`):

| Operación | Muestras | Mediana | p95 |
|---|---:|---:|---:|
| Cambio de perfil | 30 | 2,70 ms | 3,69 ms |
| Historial mientras se espera IA | 15 | 2,43 ms | 2,94 ms |
| Estado del servidor mientras se espera IA | 15 | 0,81 ms | 0,99 ms |

La creación del trabajo devolvió HTTP 202 en 1,53 ms en esa medición. Estos números describen el transporte local de prueba: no incluyen internet ni miden generación real de Gemini, ni prometen esos tiempos para otros equipos.

No había clave disponible en el entorno de herramientas. Por tanto no se ejecutó una evaluación real del proveedor ni se midió su latencia actual. El test de transporte comprueba con respuestas simuladas el contrato HTTP, reintento de 503, cuota, timeout y cancelación.

## Arranque después de actualizar

1. Detener el servidor anterior con Ctrl+C.
2. Ejecutar `python -m pip install -r requirements.txt`.
3. Ejecutar `python app.py --ask-key` y pegar la clave en la terminal.
4. Abrir http://127.0.0.1:8000 y recargar con Ctrl+F5.
5. Seleccionar perfil y analizar texto propio. La base existente se conserva.

## Límites explícitos

El modelo puede seguir tardando o estar indisponible. El refactor elimina el bloqueo local y acota la espera; no garantiza rapidez de un proveedor externo. Los trabajos tienen deadline de 40 segundos y se cancelan al cambiar de perfil. Las sesiones y trabajos son de un solo proceso; ejecutar con un worker. Un despliegue público necesitaría autenticación y un almacén compartido para trabajos/sesiones.

Los materiales académicos anteriores describen la evolución del prototipo y pueden mencionar el modo ensayo retirado. README y `docs/arquitectura.md` son la referencia operativa actual. Se conservaron los cambios que ya estaban presentes en el notebook y las notas de exposición.
